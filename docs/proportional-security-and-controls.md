# Proportional Security and Merge Controls

This document specifies the maintainer operational model, proportional security architecture, tab-by-tab GitHub UI navigation tutorials, visibility/plan capability branching, solo-maintainer merge gate contracts, and recorded verification evidence for repositories managed by `sciflow-cicd`.

---

## 1. Proportional Security Architecture

The proportional security model tailors enterprise-grade GitHub security controls to solo maintainers and small research teams. It eliminates cognitive fatigue, bot spam, and unnecessary review bureaucracy while preserving rigorous supply chain security, strict status check enforcement, and immutable Action execution.

```
                      ┌──────────────────────────────────────────────┐
                      │    Proportional Security & Merge Controls    │
                      └──────────────────────┬───────────────────────┘
                                             │
      ┌──────────────────────┬───────────────┴──────────────┬────────────────────────┐
      ▼                      ▼                              ▼                        ▼
[1. Restrained          [2. Least-Privilege           [3. Solo Merge Path      [4. On-Demand
     Dependabot]             Workflows]                    Rulesets]                Doctor Audit]
  • Monthly cadence       • Read-only default tokens    • 0 required approvals   • Inventory inspection
  • Grouped updates       • 40-character SHA pins       • Strict status checks   • CONFIGURED/MISSING/
  • Open PR limit (5)     • Explicit job scopes         • App ID pinning           UNSUPPORTED/INACCESSIBLE
  • Single monthly PR     • Broad writes rejected       • Human merge path       • Settings navigation
```

### 1.1 Restrained Dependabot Cadence & Update Grouping (`scripts/dependabot_generator.py`)

Unconstrained Dependabot configurations overwhelm solo maintainers with daily pull requests, noise, and context-switching overhead. The proportional model (`scripts/dependabot_generator.py`) stages `.github/dependabot.yml` in the draft **Setup Pull Request** with:
- **Monthly Cadence:** Dependabot is scheduled for monthly updates (`interval: "monthly"`).
- **PR Limits:** Caps open Dependabot pull requests (`open-pull-requests-limit: 5`) to avoid cluttering the repository backlog.
- **Update Grouping:** Related ecosystems group minor and patch updates (`patterns: ["*"]`, `update-types: ["minor", "patch"]`) into single consolidated pull requests under `groups:` (defaulting to `pip-dependencies` for `"pip"` and `actions` for `"github-actions"`, or custom group mappings such as `groups: all-dependencies` / `pip-dependencies` / `github-actions-dependencies`).

Example `.github/dependabot.yml` generated by `dependabot_generator.py`:

```yaml
# Dependabot configuration generated by sciflow-cicd
# Proportional security: restrained cadence and grouped semver updates
version: 2
updates:
  - package-ecosystem: "pip"
    directory: "/"
    schedule:
      interval: "monthly"
    open-pull-requests-limit: 5
    groups:
      pip-dependencies:
        patterns:
          - "*"
        update-types:
          - "minor"
          - "patch"
  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "monthly"
    open-pull-requests-limit: 5
    groups:
      actions:
        patterns:
          - "*"
        update-types:
          - "minor"
          - "patch"
```

### 1.2 Least-Privilege Workflow Tokens & Action SHA Pins (`scripts/configure_github_repo.py` & `scripts/lint_workflow_action_pins.py`)

Every workflow managed by `sciflow-cicd` adheres to defensive supply-chain standards:
- **Default Read-Only Permissions:** The `actions` and `actions-policy` stages in `scripts/configure_github_repo.py` configure repository Actions permissions (`PUT /repos/{owner}/{repo}/actions/permissions/workflow`) with `default_workflow_permissions: "read"` and `can_approve_pull_request_reviews: False`.
- **Optional Repository-Level SHA Pinning Policy:** The `actions-policy` stage supports `allowed_actions` (`"all"`, `"local_only"`, or `"selected"`) and `sha_pinning_required: true` (`PUT /repos/{owner}/{repo}/actions/permissions`).
- **Explicit Job Scopes & Immutable Action SHA Pins:** Workflows declare explicit, minimal permissions (`contents: read`, `pull-requests: read`) and pin every external Action to a full 40-character commit SHA accompanied by an inline version comment (e.g., `uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2`). Permissive wildcards (`write-all`, `read-all`) and floating tags (`@v4`) are rejected by `scripts/lint_workflow_action_pins.py` and `sciflow-cicd doctor`.

### 1.3 Capability-Gated CodeQL Default Setup (`reconcile_codeql`)

CodeQL code scanning is capability-gated before any API write is attempted:
- **Actions & Language Preflight:** `reconcile_codeql` in `scripts/configure_github_repo.py` verifies that GitHub Actions is enabled (`enabled: True` or planned in the same Policy) and inspects `GET /repos/{owner}/{repo}/code-scanning/default-setup`. If `languages` is empty (`[]`), it stops with `CodeQL default setup is unavailable: no CodeQL-supported languages detected in repository` and marks the stage `blocked` with `availability: "unsupported"`.
- **Plan & Visibility Gate:** CodeQL Default Setup is included on public repositories (`Free` plan and above), but on private repositories requires **GitHub Advanced Security (GHAS)** on an Enterprise plan. On private `Free`, `Pro`, or `Team` repositories without GHAS, `detect_repository_capabilities` and `sciflow-cicd doctor` classify `codeql` as `[UNSUPPORTED]` (`"CodeQL default setup on private repositories requires GitHub Advanced Security"`).
- **Query Suite Selection:** Supports `query_suite: "default"` (standard high-confidence rules appropriate for solo maintainers) or `"extended"` (`{"name": "codeql", "query_suite": "extended"}`).

### 1.4 Solo-Maintainer vs Collaborator Merge Path (`reconcile_gates`)

Branch rulesets (`scripts/configure_github_repo.py:reconcile_gates`) enforce strict quality and status-check gates on `refs/heads/<default_branch>` while adapting review requirements to the team size:
- **Solo-Maintainer Merge Path (`required_approving_review_count: 0`):**
  - **Interactive Setup (`sciflow-cicd`):** Enter `none` (or `solo` / `-`) at the prompt `Reviewer username (or 'none' for solo maintainer with zero required approvals)`.
  - **Policy JSON (`gates` stage):** Set `"required_approving_review_count": 0` and omit `"reviewer"` (or set `"reviewer": null`).
  - **Direct CLI (`scripts/configure_github_repo.py gates`):** Pass `--approvals 0` without `--reviewer`.
  - **Preserved Human Merge Protections:** Even with `required_approving_review_count: 0`, the ruleset enforces a human pull-request merge decision with:
    - `required_approving_review_count: 0` (no unavailable second human reviewer required)
    - `dismiss_stale_reviews_on_push: True`
    - `require_code_owner_review: False`
    - `require_last_push_approval: False`
    - `required_review_thread_resolution: True`
    - `strict_required_status_checks_policy: True`
    - `required_status_checks`: exact check context(s) pinned to the proven GitHub Actions `integration_id` (`15368`).
- **Collaborator Merge Path (`required_approving_review_count >= 1`):**
  - Requires an open `--evidence-pr` targeting the default branch, an independent `--reviewer` (`reviewer != author`) with `write`, `maintain`, or `admin` permission, and a current `APPROVED` review on the PR head commit.
- **Required Check Names & Discrepancy Prevention:**
  - Scientific and standard CI templates provide unmatrixed **Stable Status Check** anchors so skipped or matrix jobs never deadlock pull requests:
    - `status-check` — default terminal gate job for `profile-ci` (`python` / `python-scientific` and `cmake-mpi` when `status_check_name` is default).
    - `smoke-test` — supported custom `status_check_name` for C++/MPI smoke workflows (`cmake-mpi` / `cpp-hpc-mpi`).
    - `test` / `ci` — standard single-job pull request CI (`pr-ci` / `ci`).
    - `Dependency Review` — PR dependency vulnerability and license gate (`.github/workflows/dependency-review.yml`).
    - `Issue State Gate` — separate `issue-state-gate` ruleset verifying closed `## Implementation issues` (`reconcile_issue_state_gate`).
  - If a configured ruleset check name mismatches the active or staged profile workflow's declared `status_check_name`, `setup_github_repo.py` and `reconcile_gates` block the ruleset write with `Discrepancy detected: configured ruleset check '<check>' does not match profile workflow declared check '<declared_check>'`.

### 1.5 On-Demand Doctor Diagnostics (`scripts/doctor.py`)

Maintainers run `sciflow-cicd doctor --repo OWNER/REPO` (or `--json`) on demand to inspect live repository controls against desired baselines with zero mutations:
- `[CONFIGURED]`: The control is active and matches the policy baseline.
- `[MISSING]`: The capability is supported on the repository's visibility and plan but is not yet enabled or configured.
- `[UNSUPPORTED]`: The capability cannot be enabled due to repository visibility, account plan tier (e.g., private `Free`/`Pro`/`Team` repository without GHAS, or private `Free` repository for rulesets), or missing CodeQL language source.
- `[INACCESSIBLE]`: The API token lacks sufficient permissions (`Administration: read`, `Actions: read`, `Contents: read`, or `security_events` / `repo` OAuth scope) to inspect the setting.

## 2. Exact GitHub UI Navigation Tutorials

Use the exact GitHub web interface navigation paths and option labels below when inspecting settings manually, completing human-only steps, or verifying changes applied by `sciflow-cicd`.

### 2.1 Branch Rulesets and Classic Branch Protection

- **GitHub UI Navigation:**
  - **Branch Rulesets (managed by `sciflow-cicd`):** `Settings -> Rules -> Rulesets` (`https://github.com/{owner}/{repo}/settings/rules`)
  - **Classic Branch Protection (fallback reference):** `Settings -> Branches` (`https://github.com/{owner}/{repo}/settings/branches`)
- **Step-by-Step Ruleset Walkthrough (`Settings -> Rules -> Rulesets`):**
  1. Open your repository on GitHub and click **Settings** -> **Rules** -> **Rulesets**.
  2. Click **New ruleset** -> **New branch ruleset**.
  3. Under **General**:
     - **Ruleset Name:** Enter `quality-gate` (or `main-protection`).
     - **Enforcement status:** Set to **Active**.
     - **Bypass list:** Leave empty (unmanaged bypass actors block `reconcile_gates` updates).
  4. Under **Target branches**:
     - Click **Add target** -> **Include default branch** (`refs/heads/main`).
  5. Under **Branch rules**:
     - Check **Require a pull request before merging**:
       - **Required approvals:** Set to `0` for the solo-maintainer path (`required_approving_review_count: 0`), or `1`+ for multi-person teams.
       - Check **Dismiss stale pull request approvals when new commits are pushed** (`dismiss_stale_reviews_on_push: True`).
       - Leave **Require review from Code Owners** (`require_code_owner_review: False`) and **Require approval of the most recent reviewable push** (`require_last_push_approval: False`) unchecked.
       - Check **Require conversation resolution before merging** (`required_review_thread_resolution: True`).
     - Check **Require status checks to pass**:
       - Check **Require branches to be up to date before merging** (`strict_required_status_checks_policy: True`).
       - Click **+ Add checks**, select your proven check (`status-check`, `smoke-test`, `test`, or `Dependency Review`), and bind the source to **GitHub Actions** (App ID `15368`).
  6. Click **Create** (or **Save changes**).
- **Note on Private Repository Plan Limits:** Branch rulesets are included on **public** repositories under `Free` plans, but on **private** repositories require a `Pro`, `Team`, or `Enterprise` plan (`Settings -> Rules -> Rulesets` and classic protection under `Settings -> Branches` are both plan-gated on private `Free` repositories).

### 2.2 Pull Request Merge Methods & Automatic Head Branch Deletion

- **GitHub UI Navigation:** `Settings -> General -> Pull Requests` (`https://github.com/{owner}/{repo}/settings/general`)
- **Options Managed by `merge` Stage (`reconcile_merge`):**
  1. **Allow merge commits** (`allow_merge_commit`: default `false` in scientific baselines)
  2. **Allow squash merging** (`allow_squash_merge`: default `true`; required by `audit_merge_controls`)
  3. **Allow rebase merging** (`allow_rebase_merge`: default `false`)
     *(At least one of the three merge methods above must remain enabled.)*
  4. **Always suggest updating pull request branches** (`allow_update_branch`: default `true`)
  5. **Automatically delete head branches** (`delete_branch_on_merge`: default `true`; required by `audit_merge_controls`)

### 2.3 Actions Permissions, SHA Pinning, & Default Workflow Permissions

- **GitHub UI Navigation:** `Settings -> Actions -> General` (`https://github.com/{owner}/{repo}/settings/actions`)
- **Section A — Actions permissions (`reconcile_actions` / `reconcile_actions_policy`):**
  1. Navigate to `Settings -> Actions -> General` -> **Actions permissions**.
  2. Select the desired execution policy (`allowed_actions`):
     - **Allow all actions and reusable workflows** (`"all"`),
     - **Allow local actions and reusable workflows only** (`"local_only"`), or
     - **Allow select actions and reusable workflows** (`"selected"`, with `github_owned_allowed`, `verified_allowed`, and `patterns_allowed`).
  3. Check **Require actions to be pinned to a full-length commit SHA** (`sha_pinning_required: true`) when enforcing repository-wide SHA pinning at the GitHub control-plane level in addition to `scripts/lint_workflow_action_pins.py`.
  4. Click **Save**.
- **Section B — Workflow permissions (`default_workflow_permissions`):**
  1. Scroll down to **Workflow permissions** on `Settings -> Actions -> General`.
  2. Select **Read repository contents and packages permissions** (`default_workflow_permissions: "read"`).
  3. Uncheck **Allow GitHub Actions to create and approve pull requests** (`can_approve_pull_request_reviews: False`).
  4. Click **Save**.

### 2.4 Dependabot Alerts, Security Updates, & Monthly Grouped Version Updates

- **GitHub UI Navigation:** `Settings -> Code security` (or `Settings -> Code security and analysis`) -> **Dependabot** (`https://github.com/{owner}/{repo}/settings/security_analysis`)
- **Options & Files:**
  1. **Dependabot alerts (`vulnerability-alerts`):** Toggle **Dependabot alerts** to **Enabled** (`PUT /repos/{owner}/{repo}/vulnerability-alerts`). Enabling `vulnerability-alerts` in `sciflow-cicd` also enables the Dependency Graph and chains `automated-security-fixes`.
  2. **Dependabot security updates (`automated-security-fixes`):** Toggle **Dependabot security updates** to **Enabled** (`PUT /repos/{owner}/{repo}/automated-security-fixes`).
  3. **Dependabot version updates (`.github/dependabot.yml`):** Staged by `sciflow-cicd` via `dependabot_generator.py` in the draft **Setup Pull Request** with `interval: "monthly"`, `open-pull-requests-limit: 5`, and grouped minor/patch updates (`groups: all-dependencies` / `pip-dependencies` / `actions`). Once the Setup PR is merged into `main`, GitHub activates **Dependabot version updates** automatically.

### 2.5 Dependency Graph & PR Dependency Review Gate

- **GitHub UI Navigation:** `Settings -> Code security -> Dependency graph` (`https://github.com/{owner}/{repo}/settings/security_analysis`) + `.github/workflows/dependency-review.yml`
- **Setup & Availability:**
  1. On **public** repositories, **Dependency graph** is enabled automatically (`[CONFIGURED]`).
  2. On **private** repositories (`Free`, `Pro`, `Team`, or `Enterprise`), enable **Dependency graph** via `Settings -> Code security -> Dependency graph` (or by enabling `vulnerability-alerts` in `sciflow-cicd`).
  3. Stage `.github/workflows/dependency-review.yml` via the `workflows` stage (`template: "dependency-review"`, `fail_on_severity: "high"`, `allow_licenses: "MIT, Apache-2.0, BSD-3-Clause, BSD-2-Clause, ISC, Python-2.0"`).
  4. **Plan Gate:** `actions/dependency-review-action` runs on all **public** repositories (`Free` plan included), but on **private** repositories requires **GitHub Advanced Security (GHAS)** on an Enterprise plan. On private `Free`/`Pro`/`Team` repositories without GHAS, `sciflow-cicd` hides `dependency-review` from default interactive choices and `sciflow-cicd doctor` classifies `dependency_review` as `[UNSUPPORTED]`.

### 2.6 CodeQL Default Setup

- **GitHub UI Navigation:** `Settings -> Code security -> Code scanning -> CodeQL analysis -> Set up -> Default` (`https://github.com/{owner}/{repo}/settings/security_analysis`)
- **Options & Preflight:**
  1. Navigate to `Settings -> Code security -> Code scanning -> CodeQL analysis -> Set up -> Default`.
  2. Choose the query suite (`query_suite: "default"` or `"extended"`) and click **Enable CodeQL**.
  3. Via `sciflow-cicd`, include `{"name": "codeql"}` (or `{"name": "codeql", "query_suite": "extended"}`) in Policy JSON or run `python3 scripts/configure_github_repo.py --repo OWNER/REPO --apply codeql`.
  4. **Availability Requirements:** Requires Actions enabled, at least one CodeQL-supported language in the repository (`languages != []`), and either **public** visibility or **GitHub Advanced Security** on a private Enterprise repository. Note that `PATCH /repos/{owner}/{repo}/code-scanning/default-setup` returns HTTP `202 Accepted` with an asynchronous `run_id`, which `sciflow-cicd` records as `status: "pending"` (`validation_run_id`) until initial scan configuration completes.

### 2.7 Secret Scanning, Push Protection, & Private Vulnerability Reporting

- **GitHub UI Navigation:** `Settings -> Code security` (or `Settings -> Code security and analysis`) (`https://github.com/{owner}/{repo}/settings/security_analysis`)
- **Options Managed by `security` Stage (`reconcile_security`):**
  1. **Secret scanning (`secret-scanning` -> `secret_scanning`):** Available on public repositories and private Enterprise repositories with GHAS; marked `[UNSUPPORTED]` on private `Free`/`Pro`/`Team` repositories without GHAS.
  2. **Push protection (`push-protection` -> `secret_scanning_push_protection`):** Blocks `git push` containing detected secrets; shares the same public or private-GHAS requirement as secret scanning.
  3. **Private vulnerability reporting (`private-vulnerability-reporting`):** Allows security researchers to report vulnerabilities privately under `Security -> Advisories`. **Public repositories only**—on private repositories, `reconcile_security` rejects `private-vulnerability-reporting` with `private vulnerability reporting is available only for public repositories` (`availability: "unsupported"`).

### 2.8 Actions Secrets & Variables (When Optional Automation Is Selected)

- **GitHub UI Navigation:** `Settings -> Secrets and variables -> Actions` (`https://github.com/{owner}/{repo}/settings/secrets/actions` and `https://github.com/{owner}/{repo}/settings/variables/actions`)
- `sciflow-cicd` never accepts secret values on the command line or in Policy JSON. Configure these in the GitHub UI only when the corresponding optional workflow is selected:

| Credential Name | Tab under `Settings -> Secrets and variables -> Actions` | Used By Workflow | Purpose & Required Scope |
| --- | --- | --- | --- |
| `POLICY_AUDIT_TOKEN` | **Secrets** -> **New repository secret** | `.github/workflows/policy-drift-audit.yml` ([guide](policy-drift-audit.md)) | Fine-grained PAT with `Administration: read` and `Contents: write` (or classic `repo`) so the weekly Policy Drift Audit can read admin endpoints. |
| `TRIAGE_PROJECT_TOKEN` | **Secrets** -> **New repository secret** | `.github/workflows/issue-triage.yml` ([guide](workflows.md#issue-triage-workflow)) | Optional token with `project` scope to place triaged issues onto a Projects V2 board. |
| `TRIAGE_PROJECT_ID` | **Variables** -> **New repository variable** | `.github/workflows/issue-triage.yml` | Node ID (`PVT_...`) of the target GitHub Projects V2 board when automatic board placement is enabled. |

> [!NOTE]
> Provider credentials for Automated Advisory Review (`OCR_LLM_AUTH_TOKEN`, `OCR_LLM_URL`, `OCR_LLM_MODEL`, `OCR_LLM_USE_ANTHROPIC`, and GitHub App private key) are configured directly in the external VM host environment (e.g. systemd service unit or `/etc/sciflow-cicd/ocr.env`), completely isolated from repository Actions secrets and variables. See the [Advisory Review guide](advisory-review.md).

## 4. Two-Pass Merge Gate Activation & Recovery

When configuring a new repository, `workflows` / `ci-profile`, `dependabot`, and `gates` (or `issue-state-gate`) can be declared together in `.local/setup-policy.json`, but GitHub rulesets cannot bind a required status check to an `integration_id` until the workflow file is active on `main` and has executed at least once on an open pull request.

### Two-Pass Activation Walkthrough

1. **Pass 1 — Apply Direct Settings and Stage the Setup Pull Request:**
   ```bash
   sciflow-cicd dry-run --policy .local/setup-policy.json > .local/setup-dry-run.json
   sciflow-cicd apply --policy .local/setup-policy.json --dry-run-result .local/setup-dry-run.json
   ```
   - Direct API stages (`features`, `merge`, `actions`, `security`, `codeql`) apply immediately.
   - Staged files (`.github/workflows/ci.yml`, `.github/workflows/dependency-review.yml`, `.github/workflows/issue-state-gate*.yml`, `.github/dependabot.yml`) open in a single draft **Setup Pull Request** on `codex/workflows-<repo>`.
   - `gates` and `issue-state-gate` report `status: "pending"` with exit code `0`:
     - `gates`: *"Merge the draft Setup Pull Request, then provide an approved evidence PR with successful CI checks before applying this gate: .github/workflows/ci.yml"*
     - `issue-state-gate`: *"Merge the draft Setup Pull Request, then wait for a successful exact-source Issue State Gate check before applying this rule: .github/workflows/issue-state-gate.yml"*
2. **Owner Merge & Evidence PR Check Execution:**
   - In GitHub (`Pull requests` tab), mark the draft **Setup Pull Request** ready for review and merge it into `main`.
   - Open (or push to) an evidence pull request `#<N>` targeting `main` so `.github/workflows/ci.yml` (`status-check`, `smoke-test`, or `test`) and `.github/workflows/issue-state-gate.yml` (`Issue State Gate`) complete with `conclusion: "success"`.
3. **Pass 2 — Activate and Verify the Branch Ruleset:**
   - Re-run `sciflow-cicd` (selecting `1. Resume existing setup`) or run Headless Mode with `"evidence_pr": <N>`:
     ```bash
     sciflow-cicd dry-run --policy .local/setup-policy.json > .local/setup-dry-run.json
     sciflow-cicd apply --policy .local/setup-policy.json --dry-run-result .local/setup-dry-run.json
     ```
   - Or invoke the direct CLI:
     ```bash
     # Solo maintainer (0 required approvals, enforcing stable status-check):
     python3 scripts/configure_github_repo.py --repo OWNER/REPO --apply gates \
       --name quality-gate --evidence-pr <N> --approvals 0 \
       --check .github/workflows/ci.yml=status-check
     ```
   - `reconcile_gates` verifies the passing check run, pins `integration_id: 15368`, creates/updates the ruleset, reads it back, and confirms `status: "verified"` (and `no-op` on subsequent runs).

## 5. Recorded Verification Evidence (`Observed / Inferred / Unverified`)

In accordance with the repository's evidence gate, the following records separate **Observed**, **Inferred**, and **Unverified** results across disposable live repositories and automated capability/doctor contract suites (`tests/test_p3_e2e_validation.py`, `tests/test_solo_maintainer_ruleset.py`, `tests/test_p6_184_security_merge_tutorials.py`).

## 6. Collaborator Merge Path and Optional Issue State Gate

### 6.1 Collaborator Merge Path (`required_approving_review_count >= 1`)

For multi-person repositories requiring an independent human reviewer (`--approvals 1` default):

```bash
python3 scripts/configure_github_repo.py --repo OWNER/REPO gates \
  --name code-review --evidence-pr 123 --reviewer REVIEWER \
  --check .github/workflows/ci.yml=ci-check
python3 scripts/configure_github_repo.py --repo OWNER/REPO --apply gates \
  --name code-review --evidence-pr 123 --reviewer REVIEWER \
  --check .github/workflows/ci.yml=ci-check
```

`reconcile_gates` verifies that `REVIEWER` is distinct from the evidence PR author, holds `write`, `maintain`, or `admin` collaborator permission on the repository, and has submitted a current `APPROVED` review on the evidence PR's `head.sha` (not superseded by `CHANGES_REQUESTED` or `DISMISSED`).

### 6.2 Optional Issue State Gate

Policy may include `{"name": "issue-state-gate"}` to select the trusted Issue State Gate workflow suite: the primary check, issue close/reopen refresh, and operator reconciliation workflows. They are staged together in the same draft Setup Pull Request as other selected workflows. Dry-Run reports the workflow, context, source derivation, effective rule, prerequisites, and conflicts without writing. Apply leaves the rule pending until the owner merges the Setup Pull Request and a successful check from that active workflow is observable on an open pull request.

The Issue State Gate is a separate ruleset requiring pull requests and the exact required status check. It requires zero approving reviews, no code-owner review, no last-push approval, and no review-thread resolution. Required status checks do not require branch synchronization. It has no bypass actor. Existing unmanaged rules, branch conditions, required checks, or bypass actors on the managed `issue-state-gate` ruleset cause Apply to stop. After writing, `sciflow-cicd` reads the ruleset back and reports success only when the active rule exactly matches the requested check and source.
