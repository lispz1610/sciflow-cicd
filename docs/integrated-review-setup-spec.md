# Integrated Review Setup specification

**Status:** Proposed for owner review. **Scope:** Merge the private `open-code-review-setup` source into `github-repo-setup` and deliver one `gh-setup` product. This specification supersedes the independent-product portions of `docs/open-code-review-project/spec.md`; that document remains historical evidence. It does not authorize installation in a target repository.

## Product contract

`gh-setup` configures repository settings and optionally enables Advisory Review. It is the only installed command. The separate `open-code-review-setup` command is removed from the integrated distribution; its old repository remains a historical reference. Review Setup is off by default for a new repository. The first integrated release supports Review Setup for private target repositories only; public repository support is tracked in [GitHub issue #2](https://github.com/lispz1610/github-repo-setup/issues/2).

Advisory Review posts findings on pull requests. It does not approve or merge them, create a required check, or change a ruleset. The owner controls whether to merge the draft Setup Pull Request that installs it. Repository settings that GitHub exposes directly still apply directly. Every selected workflow in one setup session, including PR CI, dependency review, and Advisory Review, goes into one Setup Pull Request.

The workflow keeps the existing trusted-base `pull_request_target` design, same-repository PR guard, explicit minimum token permissions, pinned upstream Action and CLI, per-PR cancellation, timeout, token budget, and suppression of raw artifacts. It treats PR content as review data and never checks out or executes untrusted PR code with the provider secret. Fork PRs remain skipped. The review is a bring-your-own-key integration; setup never asks for or receives the provider key.

## Command and Policy contract

Running `gh-setup` with no arguments starts Interactive Setup. `gh-setup apply --policy PATH [--repo OWNER/REPO]` runs Headless Mode. Both share one normalized planning and apply path. Dry-Run is read-only and precedes every interactive write; Headless Mode retains the existing explicit policy-apply command. The CLI reports a structured outcome without printing setup tokens, provider secrets, or secret values.

Existing repository Policy version 1 documents remain accepted with their current stage semantics. Interactive Setup writes Policy version 2. A version 2 Policy has `version: 2`, optional `repository`, and a nonempty `stages` array. Existing stage names and payloads retain their version 1 meanings. A new, optional `review` stage contains the previously independent review policy's `workflow`, `llm`, and `limits` objects, using the same field validation except where this specification changes readiness behavior. The review workflow path is fixed to `.github/workflows/open-code-review.yml`. Unknown fields and unsafe combinations fail before any writes. Headless Mode requires an explicit current `expected_sha` for a changed managed workflow; an Interactive Setup update obtains the SHA from Inventory and asks the user to confirm the shown change. New Policies retain exact Action and CLI pins. Upgrading `gh-setup` never silently changes saved pins; Interactive Setup may offer an explicit pin update after verification.

The review stage stores only nonsecret provider configuration: HTTPS endpoint, model, provider protocol, fixed secret name `OCR_LLM_AUTH_TOKEN`, selected events, token budget, timeout, optional trusted rule path, retention limit, and exact pins. The required repository variables are `OCR_LLM_URL`, `OCR_LLM_MODEL`, and `OCR_LLM_USE_ANTHROPIC`. The provider key is supplied by the owner directly in GitHub Actions secrets. Policies, examples, Dry-Run output, and logs never contain the key. Existing version 1 policies from the separate review tool are historical inputs, not a second accepted top-level schema for `gh-setup`; owners can select Review Setup interactively or create a version 2 repository Policy.

## Interactive Setup

The interface remains a sequential CLI prompt, called Interactive Setup. Each step shows, before the choice, a visible explanation of its purpose, the current detected state, the consequences of each option, and the recommended default. Option explanations remain visible without a help key. Resume State preselects observed managed settings; a managed review workflow preselects Review Setup. An unmanaged review file is shown as a conflict, never treated as installed. No prompt asks for a setup token or provider key.

| Step | Required explanation and decision |
| --- | --- |
| Target and Inventory | Explain which repository will change, what permissions are needed to inspect it, and that Inventory makes no changes. Show visibility and the detected configuration before asking for selections. |
| Repository features | Explain what enabling Issues, Wiki, and Projects makes available and that unchecked existing features are left alone. |
| Merge options | Explain each merge method, branch deletion, and update-branch behavior; warn before a selection would leave no merge method. |
| Actions and security | Explain how Actions availability and token permissions affect workflows, and what each security setting enables. Identify settings that require plan or organization support. |
| Repository content | Explain labels and authored files, including which existing items may be updated and why a changed file needs its current blob SHA. |
| CI and dependency workflows | Explain what each workflow runs, what a pinned Action protects, that selected workflows are staged in a draft Setup Pull Request, and that the owner must merge it. |
| Review Setup | Explain Advisory Review, provider billing and possible content exposure in comments/logs, why the provider secret and variables live in GitHub, and why this workflow is separate from CI and never a required merge check. Default off for a new repository. |
| Review essentials | Ask for provider protocol, HTTPS endpoint, model, events, budget, and timeout with a plain-language effect and example for each option. Display the exact secret and variable names and GitHub setup path; never accept a key through the terminal. |
| Review advanced | Offer explicit Action/CLI pin updates, retention limit, and trusted rule path with explanations of risk and when to change them. Preserve current pins unless the user deliberately selects an update. |
| Rulesets and merge gates | Explain the evidence PR, reviewer, and CI checks required before a gate can be applied. State that a newly staged CI workflow leaves its dependent gate pending until merge and successful CI evidence. Never offer Advisory Review as a required check. |
| Dry-Run and confirmation | List direct setting writes separately from workflow files proposed in the one Setup Pull Request. Show warnings, blockers, pending gates, and the effect of merging the PR. Ask once for final apply confirmation, defaulting to No. |
| Result and next steps | Report verified direct settings, the Setup Pull Request URL, owner merge action, review credential/configuration tasks, pending gates, and any exact failures. Distinguish staged review from a successful Review Run. |

Interactive Setup may group related simple selections on one screen, but it must preserve the explanation for every option. For example, the review choice must say that it adds automated comments to eligible PRs, uses the owner's provider account, requires a later secret and variables in GitHub, and does not block merging. The Dry-Run must state that installing a workflow requires the owner to inspect and merge the draft PR before a Review Run can occur.

## Planning, readiness, and staging

The coordinator loads Policy v1 or v2, builds one normalized desired state, collects Inventory, validates selected settings, and renders selected workflow bytes. Workflow renderers own their templates and pins; a shared staging module owns repository reads, ownership markers, blob-SHA checks, branch/PR verification, writes, and readback. It checks the default-branch head again before writing. A workflow file is updateable only if it is recognized as managed and its expected SHA matches. A legacy review marker can be migrated with the same explicit SHA acknowledgement. An unmanaged file or divergent managed file is a conflict. A changed default head causes replanning.

The staging module proposes the exact selected workflow paths in one stable, owned branch and one draft Setup Pull Request. The branch diff may contain only selected workflow files. Before returning success, it verifies every staged byte, the branch diff, the pinned Action references, and the draft PR. If an open unified Setup Pull Request already has the exact desired contents, reuse it without writes. If its selected contents differ, report its URL and require owner resolution before another workflow proposal. Existing legacy installer PRs are linked and left untouched; they block new workflow staging until the owner resolves them. Direct settings can still proceed. Never overwrite unrelated branch changes or automatically delete a partial branch.

Readiness is separate from safe staging. Missing `OCR_LLM_AUTH_TOKEN`, missing or mismatched `OCR_LLM_*` variables, disabled or restrictive Actions policy, and excessive retention produce actionable warnings during setup and do not prevent a safe Setup Pull Request. Effective organization policy that cannot be proved is also reported as a warning about Review Run readiness. The setup tool does not silently broaden Actions permissions or lower retention. Public targets cannot stage Review Setup in this release: Headless Mode rejects an explicit public-repository review stage before any writes; Interactive Setup explains the limit and lets other selected stages continue.

The rendered review workflow must start eligible same-repository Review Runs with an explicit check for the required secret and variables. If one is absent, the job fails with a GitHub Actions error naming the missing item and the owner action, without revealing values. Other Review Run failures, including provider and Actions policy failures, remain visible in GitHub Actions logs and job status. `gh-setup` does not run a monitoring daemon or claim to observe later Review Runs. Setup may finish with **review pending configuration** and Headless Mode exits zero when the selected safe changes were applied or staged successfully and only readiness warnings remain.

## Apply ordering and outcomes

Dry-Run checks the full selected workflow bundle for safe staging before writes and reports any conflicts. After final interactive confirmation, the coordinator applies direct settings and stages the workflow bundle. It records each verified direct write and continues independent work where safe. A workflow conflict blocks the entire workflow bundle so that selected workflows are never split across draft PRs; it does not erase verified direct settings. A gate that depends on a newly staged CI workflow remains pending until the Setup Pull Request is merged and an evidence PR has successful CI. An Advisory Review job never becomes gate evidence by default.

If a direct write or staging action fails after earlier writes, preserve verified changes and report exactly what is applied, pending, blocked, or failed, with a recovery action and relevant branch/PR URL. Do not claim rollback. If a branch write began but the PR could not be created or verified, report the partial branch and require manual inspection before retrying. Repeat application against unchanged settings or a matching open Setup Pull Request performs no new writes.

## Source, documentation, and release gates

Integrate the private project's policy validation, renderer, readiness checks, GitHub API behavior, tests, examples, and operator guidance with provenance recorded in repository documentation. Adapt code around the shared coordinator and staging boundary; do not graft the complete old Git history. Remove the separate command from installation and user documentation. Mark historical independent-product documents as historical where they are linked, and update current CLI, Policy, workflow, installation, and recovery guides to describe the integrated product.

Tests must cover Policy v1 compatibility, strict v2 validation, review default/resume choices, always-visible prompt explanations, read-only Dry-Run, missing credentials as warnings, public-repository behavior, managed SHA confirmation, legacy marker migration, drift/unmanaged-file rejection, one-PR staging and exact reuse, legacy PR conflict, partial-write reporting, deferred gates, runtime missing-credential error, and advisory/fork safety. Before an integrated release is called ready, run the local suites and complete an authorized live installation in a disposable private repository: inspect and merge its one Setup Pull Request, observe a successful eligible Review Run and advisory finding, and record sanitized PR/run URLs, exact pins, provider limits, and any unverified cases. A staged or merged workflow alone is not proof that review works.
