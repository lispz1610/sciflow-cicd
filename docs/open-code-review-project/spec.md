# Open Code Review setup v1 specification

> [!NOTE] Historical Document
> This specification is preserved as historical evidence for the initial independent release. It is superseded by the [Integrated Review Setup specification](../integrated-review-setup-spec.md) for the unified `gh-setup` product.

**Status:** Approved design on 2026-10-09. **Destination:** private `lispz1610/open-code-review-setup`. This document refines the [handoff](../open-code-review-handoff.md) and is the source of truth for the implementation plan. It does not authorize deployment to a target repository.

## Purpose and boundaries

The project supplies an independent Python CLI that stages a dedicated OpenCodeReview GitHub Actions workflow in a target repository through a draft pull request. Once merged, the workflow runs by default on pull request opening, new commits, and reopening; it publishes advisory review comments. It does not approve or merge PRs, create branch protection or rulesets, or become a required merge check. The target repository owner's CI remains separate. The new CLI must have no runtime or test imports from `github-repo-setup`.

The first version uses Actions, not a GitHub App. It skips fork PRs and never checks out or executes PR code with a provider secret in the trusted workflow. It never silently enables Actions, broadens allowed Actions, changes token defaults, or configures branch protection. The owner configures the provider secret and three repository variables; the installer reads only secret metadata and exact variable values. A separately hosted App is reconsidered only after a real policy block or measured volume justifies its extra operation. See [ADR 0001](adr/0001-separate-review-workflow.md) and the [cost comparison](cost-comparison.md).

## CLI and policy contract

The CLI accepts `--repo OWNER/REPO --policy PATH [--apply]` and obtains its setup credential from `GITHUB_TOKEN`. Without `--apply`, it validates prerequisites and reports a read-only plan. With `--apply`, it writes only `.github/workflows/open-code-review.yml` to a deterministic setup branch and creates or reuses a draft PR for owner review. It prints structured results without provider keys or setup tokens. A repeat on unchanged state writes nothing. A failed partial write reports the branch and explicit recovery guidance; it never silently deletes or overwrites another person's work.

Policy version 1 has the historical top-level `version`, `workflow`, `llm`, and `limits` objects. The workflow requires template `open-code-review`, template version 1, fixed filename `open-code-review.yml`, `pull_request_target`, fork policy `skip`, a full 40-character Action commit, a pinned CLI version, positive `max_tokens_budget`, and `timeout_minutes`. Its example defaults to `opened`, `synchronize`, and `reopened`; the owner may select a nonempty unique subset of those events. It may include `expected_sha` for a managed update and `rule_path` for a trusted JSON object under `docs/` or `.opencodereview/`. The LLM policy selects an HTTPS endpoint without embedded credentials, a nonempty model, an OpenAI-compatible or Anthropic protocol, and fixed secret name `OCR_LLM_AUTH_TOKEN`. `limits.max_retention_days` bounds the target repository's artifact and log retention. Reject unknown keys and unsafe modes.

The target repository supplies Actions secret `OCR_LLM_AUTH_TOKEN` and variables `OCR_LLM_URL`, `OCR_LLM_MODEL`, and `OCR_LLM_USE_ANTHROPIC`. The latter is the lowercase string `true` or `false`; the values must match the policy. The setup credential needs the least privileges required to inspect repository/Actions settings, read content, write the selected workflow and setup branch, and open the draft PR. The user guide names the exact token permissions verified against current GitHub documentation. Provider keys must never enter policy files, fixtures, logs, or Git history. The token budget is a stop condition, not a guaranteed billing limit. Logs and comments may contain reviewed content.

This is a BYOK integration. GitHub Actions supplies the runner, not an LLM or Copilot Student model entitlement. The owner selects an API provider and model with its own access, quota, and billing. The same provider choice would be available to a separately hosted GitHub App, so model availability alone does not decide between the execution architectures.

## Workflow and preflight

The rendered workflow has explicit `contents: read` and `pull-requests: write`, a same-PR concurrency group with cancellation, a job timeout, a same-repository head condition, pinned upstream Action and CLI, `llm_extra_body: "{}"`, and raw artifact upload disabled. The selected Action must perform trusted-base checkout and treat PR code as review data only. Optional `rule_path` is read from the default branch and parsed as a JSON object before staging. Recheck upstream pins and the Action's transitive `uses` dependencies before release; the historical Action commit `182898cf522da3d04157b422752d028417974e19` and CLI `1.12.12` are starting evidence, not automatic upgrades.

Preflight verifies that Actions is enabled, the selected Action and dependencies are permitted by the effective policy, retention is within the owner's limit, the secret exists, and the three variables match. `allowed_actions: all` can pass after checking the other prerequisites. For `selected` or inherited restrictions, inspect the accessible policy and action dependency set; if effective permission cannot be proven, stop with a precise diagnostic and the required owner action. `local_only` cannot run the external Action. Never change repository or organization Actions policy automatically. Bind preflight and installation to the same default-branch head; abort and require a new run if it moves.

## Managed file and staging rules

The new renderer owns a distinct versioned marker. A workflow with the old `github-repo-setup` marker is eligible for migration only when the caller supplies its current blob SHA as `expected_sha`; the installer stages the replacement in a draft PR. A current new-marker workflow also needs `expected_sha` for changed content. Unmanaged workflow files are rejected. A missing file with `expected_sha` is drift. The selected branch diff may contain only the fixed workflow path. Before reporting success, verify the pinned Action reference, branch diff, staged blob, and draft PR readback. Repeated dry runs and applies against the same proposed or merged content must create no additional writes.

## Verification and release boundary

The new repository has an isolated test suite with owned fake GitHub API fixtures. It covers policy validation, workflow rendering, preflight failures, dry run without writes, apply and readback, drift and legacy migration, partial-write recovery, repeated setup, no cross-repository imports, fork skip, trusted rule file, and advisory behavior. No credential values appear in committed examples or evidence.

Before calling v1 ready, use a disposable target repository and an authorized provider key to perform dry run, apply, inspect and merge the workflow draft PR, open a same-repository PR, observe a review that uses an unchanged project file, update and reopen the PR to check triggers and cancellation behavior, exercise fork skip, and repeat setup without writes. Record sanitized repository, PR, and run URLs plus exact pins, quota limitations, and observed review text. Separate local fixture results from live observations; label any unavailable live case unverified. The setup project stays private, maintained by `lispz1610`, with no public license grant in v1. Its README records supported Python versions, installation, manual GitHub setup, security reporting contact, and a release process based on passing isolated and live gates. Once ready, update `github-repo-setup` to link to the new location and run its retained suite.
