### Validation & publication boundary summary

In alignment with [`README.md`](../README.md#distinguishing-pr-smoke-checks-real-gpuhpc-validation-and-publication-workflows), `gh-setup` separates:
1. **Ordinary Python/C++ pull-request smoke checks** (`status-check`, `smoke-test`, `test` on `2–4` vCPU ephemeral `ubuntu-24.04` runners with oversubscribed MPI and CPU fallbacks), which verify compilation, unit tests, and MPI collective ordering on CPU.
2. **Real GPU/HPC hardware validation** (executed externally on Google Colab or dedicated cluster hardware; never claimed by GitHub-hosted CI).
3. **Publication workflows** (`release-promotion.yml`, `CITATION.cff`, 5-state DOI governance, SPDX 2.3 `sbom.spdx.json`, and `container-publish.yml`), which package, cite, and archive verified software artifacts but **do not prove numerical/scientific reproducibility**.

## Removal and rename semantics (this issue)

- Skill-level removals and renames are **blocked by default** with an actionable error that names the dropped skills and the required acknowledgment.
- Acknowledgement is `allow_removed_skills` in the `agent-skills` Policy stage; it must list **exactly** the skills the new catalog drops, otherwise the whole workflow-and-skills bundle is blocked before any write.
- Acknowledged removals are staged as deletions (local file unlink with empty-directory pruning; remote `DELETE` inside the draft Setup Pull Request), guarded by prior-manifest hashes so locally edited or unowned skills are never deleted.
- A rename is a removed skill whose per-skill file inventory (relative filename to SHA-256 digest) exactly matches an added skill; it is reported as a `{"from", "to"}` pair in `agent_skill_upgrade`. Any edit to a skill file turns the change into a removal plus an addition instead of a rename, which falls under the default removal block and requires `allow_removed_skills` acknowledgment.
- When nothing is dropped, `allow_removed_skills` is ignored, so repeat runs stay idempotent no-ops even with stale configuration.

## Readiness reporting (this issue, source #100)

Before skills are staged, `run_policy` reports whether the repository has the
prerequisites the skills assume: issue tracker configuration
(`docs/agents/issue-tracker.md`), triage label vocabulary
(`docs/agents/triage-labels.md`), and domain documents
(`docs/agents/domain.md` plus `GLOSSARY.md`). Missing prerequisites produce
clear warnings stating that staging the skill bundle does **not** complete
repository setup, and point at the `setup-matt-pocock-skills` skill.

## Known limitations (readiness and compatibility reporting)

- `probe_cli_tools` probes the machine running setup (`shutil.which` over `PATH`), not the target repository nor the runner where skills eventually run. A CLI present at setup time but absent at runtime yields a false "ready"; a CLI absent at setup time but present at runtime yields a false "requires-manual-setup". Treat tool readiness as a setup-machine hint, not a target-repo guarantee.
- Convention detection matches required document paths as substrings of skill text (`path in text`). A casual mention of a convention path (for example `docs/agents/issue-tracker.md`) counts as a required convention, so passing references can inflate requirements and produce a false "requires-manual-setup". Only backticked CLI commands, literal convention paths, and backticked sibling skill references are grounded; substring matching has no intent awareness.

- Each source item is mapped to an existing P5 sub-issue (PR #166) or implemented here: covered by this table.
